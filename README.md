# OmniBundle

**One tool for every bundler.** Analyse a build's output — `stats.json`, source
maps, esbuild metafiles, or a plain `dist/` folder — and get one size story
across webpack, rspack, Vite, Rollup and esbuild, in a fraction of the memory.

[English](README.en.md) · [中文](README.zh.md) · [日本語](README.ja.md) · [Deutsch](README.de.md)

Status: **Phase 1 in progress.** The CLI surface and the data contracts are
frozen; the ingest, fusion and report engines are being built against them. The
binary currently reports what it can and never invents numbers.

## What it will do

```bash
npx omnibundle ./dist
# → omnibundle-report.html   one self-contained file, no network requests
# → exit 0, or exit 1 with OB0040 when a size budget is breached
```

- **One graph, every bundler.** webpack/rspack `stats.json` gives the dependency
  structure; source maps give real byte attribution; esbuild metafiles give the
  module graph. OmniBundle merges them into a single unified graph.
- **Two diagnostics the reference tools cannot produce.** *Ghost code*:
  declared by the bundler but accounted for by no mapping (tree-shaking
  misses). *Hidden code*: generated bytes that map back to no module (inlined
  snippets, `eval`, injected polyfills).
- **It fits in memory.** Measured: 1,049 MB `stats.json` parsed in **2.78 s at
  59 MB RSS**, against **176.3 s at 1,437 MB** for `webpack-bundle-analyzer` on
  the same input.
- **Budgets that fail CI.** `omnibundle.config.json` limits per chunk, per
  package or in total; a breach exits non-zero.

## Why it is built this way

Every design decision traces to a measurement, not a preference:

| decision | evidence |
|---|---|
| streaming JSON ingest, not `simd-json` | `simd-json` needs the whole document in memory — that is the ceiling we are removing ([ADR-0001](docs/decisions/ADR-0001-streaming-over-simd-json.md)) |
| our own HTML report, no vendored viewer | a viewer we do not control cannot show fusion data ([ADR-0002](docs/decisions/ADR-0002-self-built-report.md)) |
| rayon for size/gzip work, serial parsing | 25,600 assets: 2,177 ms → **342 ms (6.4x)**; the parse is already not the bottleneck |
| claims stated per phase | only the parse segment is measured today; the rest is marked `unverified` until the harness proves it |
