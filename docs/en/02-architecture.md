## 1. Crates

```
omnibundle-core    pure logic: ingest, fusion, report payload. No IO, no CLI,
                   no async runtime. This is what Phase 2 compiles to WASM.
omnibundle-cli     the `omnibundle` binary: scanning, budgets, file output.
omnibundle-wasm    Phase 2 bindings. Currently a schema-version shim only.
```

The core crate's IO-free rule is not stylistic. It is the reason a browser build
is a packaging change instead of a rewrite, and it is enforced by review
(`docs/contracts/OWNERS.md`).

## 3. Why the ingestion is streaming, in one paragraph

A 1 GB `stats.json` is not a data structure, it is a stream. The reference
implementation deserialises `stats.modules` element by element through a custom
`DeserializeSeed`, keeps only the six fields we need, and lets serde skip
everything else (including the embedded `source` strings) without allocating.
Measured: 1,049 MB in 2.78 s at 59 MB RSS, against 1,437 MB for the Node tool
that does the same job. Anything that materialises the document puts a ~2 GB
floor under the process and re-creates the problem we are solving.

## 4. The join problem (the one that decides whether fusion works)

A `.map` file does not know about webpack modules, and a `stats.json` does not
know about original sources. They are joined by:

1. **module key**: `identifier` when present, else `"{chunk_id}:{name}"`. Chosen
   for stability across rebuilds with no source change.
2. **source → module**: longest-common-suffix matching on normalised paths
   (`\` → `/`, strip the map's directory, drop `./`). Bundlers rewrite paths;
   suffix matching is what survives that.
3. **unmatched → diagnostics, never silent drops**. A generated byte that
   belongs to no module is `hidden_sources`; a module no map accounts for is
   `ghost_modules`. Silently discarding either would make the tool lie.

The full rules, including the invariant the CLI enforces before writing
anything, are in `docs/contracts/unified-graph.md`.

## 5. Size dimensions and honesty about them

Four numbers can describe "how big is this": what the bundler claimed (`stat`),
what the file actually weighs (`parsed`), what it weighs gzipped (`gzip`), and
what the original sources account for (`attributed`). They disagree, sometimes
a lot, and the disagreement *is* the insight.

The report displays one dimension at a time and always states which. If only
some assets are mapped, the whole report falls back to `parsed` rather than
mixing ground truth with estimates — a report that looks smaller than reality is
the worst thing this tool could do.

## 6. Parallelism

Three places, in order of value:

| stage | strategy | measured |
|---|---|---|
| gzip / size measurement | rayon over assets | 2,177 ms → 342 ms, 6.4x |
| size attribution (per module/source) | rayon over modules | WS-2 |
| parsing | deliberately **serial** — a single streaming pass; parallelising it would mean buffering | 1 GB at 2.78 s already |

The last row matters: the instinct to parallelise the parser is wrong here. The
parse is already faster than the reference tool's total runtime; the wins are in
memory and in the stages after it.

## 7. Caching

`.omnibundle-cache/` keyed by `blake3` over the input bytes (and, for the
merged graph, over the ordered artifact list). A cache hit is therefore provably
about identical input, not about a timestamp. Cache entries store the parsed
graph, not the rendered report, so a re-render with a different dimension costs
no re-parse.

## 8. Error and exit-code model

Errors are values (`core::Error`), not panics — a panic in a build tool is a bug
report. The CLI maps them to the exit codes in `docs/contracts/cli-surface.md`;
the important distinction is exit `1` (a size regression, i.e. the CI gate fired)
versus exit `3` (we could not read your build). A broken build must never look
like a size regression.

## 9. Dependencies (Phase 1)

| crate | role | why this one |
|---|---|---|
| `serde` / `serde_json` | ingest | custom seeds for streaming; ignored fields without allocation (ADR-0001) |
| `rayon` | parallelism | work-stealing, no runtime; 6.4x on the measured gzip stage |
| `flate2` | gzip sizes | must byte-match the reference tools; level pinned to 6 |
| `blake3` | cache keys | content addressing, fast enough to hash on the fly |
| `memmap2` | large file views | avoids a copy when a file must be read whole |
| `clap` | CLI | derive API, flag alignment with the reference tools |
| `thiserror` / `anyhow` | errors | typed in core, contextual at the CLI edge |

Nothing else. No template engine (ADR-0002), no serialisation framework, no
plugin system, no async runtime.

## 10. Extension points (declared, not built)

- `sizes::AssetSource` exists so the core can measure assets without doing IO.
  The CLI implements it from the filesystem; the WASM build will implement it
  from an in-memory `Map` handed over by the browser.
- The report payload is a plain `serde_json::Value`, so a future renderer (WebGL,
  a BI uploader) consumes the same data with no core change.
- Diagnostic `data` is open JSON, so new analyses can ship findings without a
  schema bump — as long as the `code` is registered in the contract table.
